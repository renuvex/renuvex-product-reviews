# Existing AI Rules & ikas CLI Instructions

## Summary
Inventory of pre-existing AI/agent instruction files and ikas CLI configuration **already in the project before this wiki was created**. These files are the canonical project rules — this wiki extends them, it does not replace them. Most of these files are **gitignored** (per `.gitignore` "AI/IDE tool configs & instructions" section), so they may not appear in fresh clones / CI.

Each run also adds another `<!-- Generated by Ruler --> / <!-- Source: AGENTS.md -->` header pair to `AGENTS.md` (because Cursor's adapter rewrites the source as its output). Tolerable cosmetic — periodically clean up by hand if it gets long.

## Canonical rules from existing CLAUDE.md / AGENTS.md (paraphrased — full content in those files)

### Core principles
- Prefer simplicity, readability, explicitness; small testable functions.
- TypeScript strict — avoid `any`. Use precise types from generated GraphQL.
- Treat tokens and secrets as sensitive. Never log them.

### Stack as documented in those files
- Next.js 15 App Router, React 19, TypeScript, Tailwind v4 + shadcn/ui.
- ikas Admin GraphQL via `@ikas/admin-api-client` with codegen.
- iron-session for OAuth state cookie.

> ⚠️ **Note**: these files say "Next.js 15", but `package.json` shows `"next": "16.2.1"`. The project has been upgraded; the rule files lag. This wiki uses the actual version (16.x). See [[Open_Questions]].

### MCP usage (canonical)
- **shadcn MCP** — use to fetch component boilerplates and demos before adding new UI primitives under `src/components/ui/*`.
- **ikas MCP** — for any new GraphQL operation:
  1. Run **list** tool to find the operation name
  2. Run **introspect** tool to get its full shape (variables, return fields, enums)
  3. Only then add the document to [src/lib/ikas-client/graphql-requests.ts](src/lib/ikas-client/graphql-requests.ts) and run `pnpm codegen`

### GraphQL workflow (enforced)
- **Never write inline GraphQL strings** inside API routes or components.
- Always import `gql` documents from `graphql-requests.ts`.
- Always run `pnpm codegen` after editing `graphql-requests.ts`.
- Always invoke ikas operations through `ikasClient.queries.<name>()` or `ikasClient.mutations.<name>(variables)` — keeps types.
- Reject PRs that introduce raw GraphQL outside `graphql-requests.ts`.

### API conventions (enforced)
- API routes under `src/app/api/*` validate session via `getUserFromRequest` and fetch the OAuth token via `AuthTokenManager`.
- **Never call ikas APIs from the browser.** Always proxy through server routes.
- Keep UI logic in `src/components/*`; avoid business logic in pages.
- Standard response shape: `{ data: { ...yourData } }` (or `{ error }` with status).

### Iframe page pattern (mandatory for any page that loads inside ikas Admin)

#### Frontend
1. Always call `AppBridgeHelper.closeLoader()` in a separate `useEffect(() => { AppBridgeHelper.closeLoader(); }, [])` on page mount.
2. Always retrieve the JWT via `TokenHelpers.getTokenForIframeApp()`.
3. Never make direct ikas API calls from the frontend.
4. Use the `ApiRequests` helper ([src/lib/api-requests.ts](src/lib/api-requests.ts)) to call backend.
5. Pattern: AppBridgeHelper.closeLoader() → TokenHelpers → ApiRequests → backend route → ikas client.
6. Wrap any `useSearchParams()` usage in a `<Suspense>` boundary (Next.js requirement, still applies in Next 16).
7. Handle loading + error states gracefully.

#### Backend
1. Create endpoint under `/api/ikas/*` for ikas-related operations.
2. `getUserFromRequest(request)` to extract `authorizedAppId` and `merchantId`.
3. `AuthTokenManager.get(authorizedAppId)` for the OAuth token.
4. `getIkas(authToken)` to build the GraphQL client.
5. Return `{ data: { ...response.data } }` on success; `{ error }` with status on failure.

#### Adding a new iframe endpoint
1. Create `src/app/api/ikas/<name>/route.ts`.
2. Add helper to [src/lib/api-requests.ts](src/lib/api-requests.ts) using the existing `makeGetRequest` / `makePostRequest` pattern.
3. Call from frontend via `ApiRequests.ikas.<name>(token, params)`.

### Security and privacy (enforced)
- `getIkas` uses `onCheckToken` to auto-refresh expired tokens. Don't expose tokens in responses or logs.
- TokenHelpers caches tokens in `sessionStorage` with expiration validation.
- JWT carries `authorizedAppId` (aud) and `merchantId` (sub).
- OAuth callback validates HMAC-SHA256 code signature via `TokenHelpers.validateCodeSignature(code, signature, clientSecret)`.
- State parameter validation is optional but recommended for additional CSRF protection.

### Quality gates
- `pnpm codegen` after every `graphql-requests.ts` change.
- TypeScript + ESLint clean before committing.
- Reject raw GraphQL outside `graphql-requests.ts`.
- Keep naming consistent with `ikas` brand and command patterns.

### Commit messages — Conventional Commits
Format: `<type>(<scope>): <short summary>` (max 72 chars, imperative mood).
Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
Scope: optional, lowercase, module name.

Examples (from existing rules):
- `feat(cart): add discount code validation`
- `fix(auth): prevent token refresh loop`
- `docs(readme): update installation guide`

### Wiki update logging (added 2026-05-05 — under "Project Memory / Obsidian Wiki Rules" in AGENTS.md)
- Log wiki updates **only when genuinely useful for long-term project memory** — not for every tweak.
- When a meaningful change (code, architecture, DB, API, widget, ikas integration, bug, feature, status) triggers a wiki edit, **bump the page's frontmatter `updated: YYYY-MM-DD`**.
- For changes important enough to remember as historical memory, also add a short entry under a `## Change Log` (or `## Update History`) section at the bottom of the affected page. Create the section if missing.
- Each changelog entry should include: date, short summary, related source files (if any), related ADR/bug/feature note (if any).
- Skip changelog entries for tiny visual-only edits, copy tweaks, formatting-only changes, or low-impact refactors that don't affect architecture / behavior / features / API / DB / widgets / ikas integration / bugs / project status.
- Keep entries short, factual, accurate. Don't fabricate history.
- If unsure whether a wiki update is needed, explain the judgment in the response — don't update unnecessary files.

## ikas CLI specifics

- **Config file**: `.ikas/config.json` holds `appName`, `clientId`, `clientSecret`. **Never commit, never document the secret.** This file is gitignored.
- **`ikas.config.json`** (tracked, project-root) defines local dev port (3000) and OAuth callback path (`/api/oauth/callback/ikas`). Used by the ikas dev server / CLI when starting the app locally.
- **Run command**: `pnpm run dev` (declared in `ikas.config.json`).

## How this wiki and the existing files relate

- **Existing files (CLAUDE.md / AGENTS.md / .cursor/rules)** = imperative agent rules — what to always do, what to never do.
- **This wiki (`docs/wiki/`)** = explanatory + status — what the code is, why it's that way, what's open.
- Both are needed. The agent rules are short and prescriptive; the wiki is long and descriptive.
- When they conflict: **existing rules win** for behavior; the wiki gets updated.

### When you change agent rules
1. Edit the source — currently appears to be `/AGENTS.md` at project root.
2. Run `pnpm apply:ai-rules` to regenerate `CLAUDE.md`, `.cursor/rules/*.mdc`, etc.
3. **Update this page** if the rule additions change canonical behavior.
4. **Update the relevant wiki page** ([[Claude_Code_Rules]], [[Ikas_API_Notes]], etc.) to keep cross-refs current.
