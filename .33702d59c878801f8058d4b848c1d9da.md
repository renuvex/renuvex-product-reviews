# E‑Ticaret Yorum/Değerlendirme Uygulamaları Üzerine Teknik ve Güncel İnceleme: Judge.me, Yotpo, Loox ve Benzerleri

## **Yönetici Özeti**

Bu rapor, e‑ticarette ürün/mağaza değerlendirmesi (rating) ve inceleme (review) toplayıp sergileyen uygulamaların (özellikle **Judge.me**, **Yotpo**, **Loox**) teknik olarak nasıl çalıştığını; tipik mimarileri, tema bağımsız widget enjeksiyon yaklaşımları, entegrasyon/pitfall’lar, performans ve güvenlik/GDPR boyutunu “uygulayıcı geliştirici” perspektifiyle ele alır. Yotpo’nun “widget tabanlı” kurulumunun yanında “API‑tabanlı headless” yaklaşımı da doğrudan resmi dokümantasyona dayanarak incelenmiştir.

Üç satıcı arasında teknik ayrışma çoğunlukla iki eksende olur: (1) **storefront yerleştirme modeli** (Shopify OS 2.0 app block/app embed vs. manuel snippet/placeholder) ve (2) **veri entegrasyonu modeli** (yalnızca platformun yerleşik entegrasyonu vs. kamuya açık CDN/widget API + sunucu tarafı “özel entegrasyon” API’ları + webhooks). Örneğin Yotpo, custom platformlar için “backend verisini Core API v3 ile senkronlayın, ardından storefront’ta core script+widget yerleştirin” diye açıkça iki parçalı (backend/frontend) bir kurulum tanımlar; bu da headless/cross‑platform senaryolara uygundur.

Fiyatlama ve ölçeklenme açısından **Judge.me** resmi olarak “ücretsiz plan + aylık 15 USD (tavan) düz fiyat” yaklaşımıyla ayrışır; ayrıca hız odaklı “Cache Server” seçeneğinin Awesome plan ile geldiğini ve güncellemelerin dakikalar içinde yansıdığını, ücretsiz planda CDN üzerinden “Widget API” güncellemelerinin ~20 dakikaya kadar uzayabildiğini belirtir.  **Loox** Shopify tarafında plan bazlıdır ve ölçek planının sipariş hacmiyle artan ücretlendirme detaylarını resmi yardım dokümanında yayımlar.  **Yotpo** Shopify App Store listesinde sipariş hacmine göre değişen planlar ve “harici ücretler” olabileceğini açıkça not eder; ayrıca ücretsiz planda bile “sentiment & profanity check” gibi kalite filtreleri listeler.

Tema uyumluluğu açısından kritik teknik gerçek şudur: Modern Shopify ekosisteminde “theme app extensions / app blocks / app embed blocks” yaklaşımı, manuel “script tag enjekte etme” yaklaşımına kıyasla daha kararlı ve denetlenebilir bir yerleşim sağlar; Shopify resmi dokümantasyonu, theme app extensions’ın (örn. ürün incelemeleri gibi) dinamik öğeleri tema koduna doğrudan dokunmadan eklemek için tasarlandığını vurgular.  Bu raporda, widget enjeksiyonunun DOM/CSS/yerelleştirme/a11y açısından “tema bağımsız” stabil kalması için uygulanabilir teknik desenler (MutationObserver, event delegation, lazy loading, erişilebilirlik semantiği, script yükleme stratejileri) ve somut vanilla JS örnekleri sunulmuştur.

## **İnceleme Uygulamalarının Çalışma Biçimi ve Tipik Mimari**

Bir “reviews app”i teknik olarak iki uçtan oluşur: **(A) storefront çalışma zamanı (client‑side)** ve **(B) veri/iş mantığı (server‑side)**. Yotpo, “tam yetenek seti için backend + frontend entegrasyonu” şeklinde bunu açıkça ifade eder; iki taraf “decoupled” olduğundan ayrı ayrı uygulanabilir.

**Client‑side (storefront)** tipik bileşenler:

- Tema içine eklenen **core/loader script** (çoğunlukla `async` yüklenir) ve sayfada yer alan **placeholder DOM düğümleri** (data‑attribute’lar ile product id, URL, isim vb. taşır). Örn. Yotpo Reviews Widget 3.0 loader’ı `cdn-widgetsrepository.yotpo.com` üzerinden `async` yükler ve `languageCode` parametresiyle dil bilgisini temadan geçirir; widget ise `yotpo-widget-instance` sınıfı ve `data-yotpo-*` alanlarıyla sayfaya yerleştirilir.
- SPA/dinamik içerik senaryolarında, DOM’a yeni widget placeholder eklendiğinde yeniden “init/render” gerekebilir; Yotpo, SPA kurulumunda her yeni `div` eklendiğinde `yotpoWidgetsContainer.initWidgets()` çağrısını açıkça ister.
- Shopify OS 2.0’da uygulamalar çoğunlukla **app block** veya **app embed** ile yerleştirilir; Shopify bunların tema koduna müdahale etmeden dinamik öğeler eklemek için tasarlandığını belirtir.

**Server‑side (vendor backend + platform entegrasyonu)** tipik bileşenler:

- Ürün/sipariş/müşteri verisini uygulamaya aktaran entegrasyon katmanı (Shopify gibi platformlarda genellikle platformun API/webhook mekanizmaları; custom platformlarda doğrudan “merchant backend → vendor API”). Yotpo, Core API v3 ile ürün kataloğu ve siparişlerin gönderilmesini “otomatik review request email” için gerekli görür ve fulfilment alanlarını (örn. `fulfillment_date`, `fulfillment_status=success`) özellikle vurgular.
- Review request otomasyonu (sipariş fulfilment sonrası belirli gecikmeyle e‑posta tetikleme); Yotpo, review request’in fulfilment tarihinden sonra gönderildiğini belirtir; hatta “Create order” üzerinden iptal objesi gönderilirse planlanan review request’lerin iptal edileceğini not eder.
- Veri depolama: İnceleme kayıtları (rating, metin, başlık, zaman damgası, doğrulama statüsü), reviewer profili/kimliği, ürün bağlantıları, medya (foto/video), moderasyon olayları. Bu iç veri şeması satıcıdan satıcıya değişir ve çoğu ayrıntı (örn. fiziksel DB seçimi, indeks stratejisi, medya saklama altyapısı) açıkça yayımlanmaz; bu rapor bu tür “özel iç detayları” varsayım yapmadan ele alır.

### **API, token ve veri erişimi deseni**

Modern satıcılar, public JS ortamında çalışacak “kamuya açık token” ile sunucu tarafında saklanması gereken “özel token” ayrımını açıkça yapar. Judge.me, API token’ları arasında **Public API Token (GET/Widget API için, public JS’e uygun)** ve **Private API Token (read/write, yalnızca server‑side)** ayrımını dokümante eder; ayrıca API’nin bazı sınırlamalarını (örn. API ile oluşturulan review’lerin verified olarak işaretlenememesi) belirtir.  Bu ayrım, “browser içinde secret saklama” gibi güvenlik hatalarını önlemek için temel ilkedir.

Yotpo tarafında custom platform kurulumunda kimlik doğrulama için UToken üretimi ve Core API çağrıları vurgulanır.  Headless senaryoda ise Yotpo, widget kullanmadan UGC API üzerinden “bottomline (ortalama yıldız/yorum sayısı)” gibi verileri çekmeyi örnekler ve CDN tabanlı bir endpoint şemasını gösterir.

### **Moderasyon, spam önleme ve doğrulama**

Review sistemleri, “kalite”yi üç katmanda yönetir: (1) otomatik filtreler (spam/profanity/sentiment), (2) yayınlama kuralları (auto‑publish/manuel onay), (3) doğrulama (verified purchase / order match).

- Judge.me, yeni review’leri otomatik yayınlama veya rating’e göre filtreleyerek yayınlama gibi “Publishing and moderation” ayarlarını sunar. Ayrıca “spam filter” özelliğini (plan bağımlılığıyla) ve spam olarak işaretlenen review’leri yönetmeyi dokümante eder. Verified etiketi için “manuel işaretlemiyoruz; kriterler karşılanırsa otomatik uygulanır” şeklinde net bir politika yayımlar; doğrulama statüsü dokümanında da akış/etiketleri açıklar.
- Loox, “Review Integrity & Fraud Prevention Policy” dokümanında sahte/manipüle review’a karşı sıfır tolerans, rapor inceleme süreci, “internal data (review metadata & purchase records)” ile değerlendirme gibi pratikleri açıklar. Loox yönetim arayüzünde review yanıtlama, featured review, medya yönetimi gibi moderasyon aksiyonlarını da yardım dokümanında anlatır.
- Yotpo’nun Shopify App Store listelemesinde “Sentiment and Profanity Check” özelliği plan özellikleri arasında yer alır; bu, spam/kalite filtresinin ürünleşmiş bir versiyonudur.

### **Güvenlik, gizlilik ve GDPR**

Review uygulamaları, mağaza sahibi (merchant) adına son kullanıcı verisini işlediği için genellikle **processor** rolüne düşer; merchant ise çoğu senaryoda **controller** rolündedir. Bu çerçeve, GDPR metninde “processor” için sözleşmesel/yapısal yükümlülüklerle tanımlanır (örn. madde 28).  Türkiye’de (TR) GDPR metninin Türkçe çevirisine kamu kaynağı olarak AB Başkanlığı sayfası referans verilebilir.

Satıcı bazında resmi uyum materyalleri:

- Judge.me, GDPR uyum yaklaşımını özel bir yardım makalesinde anlatır ve alt‑işleyen (sub‑processor) listesini ayrıca yayımlar.
- Yotpo, Data Processing Addendum (DPA) ve Sub‑processor listesini resmi sayfalarında yayımlar.
- Loox, Data Processing Addendum’da (son güncelleme: Oct 2024) alt‑işleyenleri listelediği sayfaya link verir, denetim (audit) katkısı, ihlal bildirimi, silme talepleri ve uluslararası transfer yaklaşımını metinleştirir. Loox ayrıca bug bounty politikasında kapsamın “public widgets embedded on merchant stores” ve “Loox APIs and backend services”i içerdiğini yazar; bu, güvenlik olgunluğu sinyali olarak değerlendirilebilir.

## **Tema Bağımsız Widget Enjeksiyonu ve UI Stabilitesi**

Tema bağımsız stabilite hedefi şu anlama gelir: Widget; farklı tema DOM hiyerarşilerinde, farklı CSS reset/utility setlerinde, dinamik section re-render’larında (Shopify section editing, AJAX cart, quick view), SPA route değişimlerinde ve farklı dil/para birimi kurulumlarında **bozulmadan** görünmeli ve etkileşimleri çalışmalıdır. Bu hedef, “tek bir ideal DOM noktası” varsayımını kırar; bunun yerine **çok adımlı yerleştirme stratejisi** uygulanır.

### **Shopify OS 2.0 yerleştirme: App blocks ve app embeds**

Shopify, Theme App Extensions’ın (app blocks/app embed blocks) “merchant’in Liquid koduna dokunmadan dinamik öğeler eklemesi” için tasarlandığını söyler; ürün incelemeleri bunun tipik örneklerindendir.  App block yaklaşımının teknik faydası, widget anchor’unun tema geliştiricisi/merchant tarafından görsel editörde belirlenmesi ve “DOM selector kırılganlığının” azalmasıdır. Ancak Shopify, `@app` block’larının “statically rendered sections” içinde desteklenmediğini belirtir; bu, bazı vintage/özel section türlerinde “block görünmüyor” gibi uyumluluk sorunlarına yol açabilir.

Bu yaklaşım, Loox ve Judge.me dokümantasyonunda “tema editöründen app block ekleyin / app embed’i açın” şeklinde görünür: Loox Reviews Widget’ı tema editöründe “Add section → Reviews Widget” app block ile ekletir; Loox Core Script ise app embeds menüsünden toggle edilir.  Judge.me de vintage temalarda app embed aktivasyonunu adım adım anlatır.

### **Platform bağımsız (arbitrary theme / headless / dış domain) yerleştirme: Placeholder + loader**

Platform bağımsız modelde ortak desen şudur:

1. Bir **loader script** (genellikle `async`) yüklenir.
2. Sayfaya **placeholder** HTML eklenir (sınıf + `data-*` alanları).
3. Loader, placeholder’ları tarar ve widget’ı render eder.

Somut resmi örnekler:

- **Yotpo (Shopify widget 3.0)**: Loader `<script src="https://cdn-widgetsrepository.yotpo.com/v1/loader/{{app_key}}?languageCode={{ localization.language.iso_code }}" async></script>`; widget placeholder `div.yotpo-widget-instance` + `data-yotpo-product-id`, `data-yotpo-url`, `data-yotpo-image-url` vb.
- **Judge.me (platform-independent widgets)**: Star badge ve legacy review widget için `jdgm-widget ... data-id="product-id"` biçiminde placeholder örnekleri yayımlanır.
- **Loox (Shopify dışında barındırılan sayfalar)**: Varsayılan olarak Shopify dışı domain’leri engellediğini, görünmesi için domain allow‑list gerektiğini yazar; loader `//loox.io/widget/loox.js?shop=STORE.myshopify.com` ve placeholder olarak `#looxReviews[data-product-id]` ya da `data-loox-aggregate` ile store‑wide görünüm, ayrıca `.loox-rating[data-fetch]` örneklerini verir.

> *Kritik not: Bu enjeksiyon modeli, widget’ın “arbitrary DOM” üzerinde çalışması anlamına gelir; dolayısıyla stabilite için “DOM gözlemi”, “yeniden başlatma” ve “çakışma önleme” teknikleri çoğu zaman zorunludur. Yotpo’nun SPA yönergesindeki `initWidgets()` ihtiyacı bunun resmi bir göstergesidir.*
> 

### **DOM yerleştirme stratejileri**

Pratikte 3 yaklaşım öne çıkar:

**Yaklaşım A — Deterministik Anchor (en stabil):**

Tema editörü/app block ile “ürün başlığı altı / fiyat altı / tab alanı” gibi sabit yerleştirme. Shopify theme app extensions bunun için tasarlanmıştır.

**Yaklaşım B — Çoklu Selector + Fallback:**

Kod, birden fazla olası anchor selector’u dener; bulamazsa “güvenli fallback” (örn. `main`, `#MainContent`, `body` sonu). Bu yöntem özellikle vintage temalarda gereklidir; Judge.me, bazı temalarda collection page yapısını tanımadığında otomatik “Install” butonunun görünmeyebileceğini ve manuel Liquid kodu ile yerleştirme gerektiğini söyler.

**Yaklaşım C — Placeholder‑first (minimum müdahale):**

Tema geliştiricisi yalnızca placeholder koyar; widget kendi konumunu değiştirmez. Bu, farklı temalarda en az sürpriz üretir; fakat merchant’ın “otomatik konumlandırma” beklentisini karşılamayabilir.

### **CSS çakışmalarını azaltma: namespace, scope ve Shadow DOM/iframe tartışması**

Review widget’ları, tema CSS’inin (reset, typography, button styles) altında çalıştığından; satıcılar çoğunlukla **class namespace** (örn. `jdgm-*`, `loox-*`, `yotpo-*`) ile çakışmaları azaltır; ancak reset/utility stilleri yine de istenmeyen sonuçlar doğurabilir. Bu noktada 3 teknik araç seti vardır:

1. **CSS namespace + düşük özgüllük (specificity) stratejisi:** BEM benzeri prefiksler, `:where()` gibi düşük specificity seçiciler, CSS variable tabanlı theme‑matching.
2. **Shadow DOM ile kapsülleme:** Shadow DOM, bileşen iç DOM’unu sayfa CSS/JS’inden izole etmeye yarar; bu izolasyon mekanizmasının varlığı ve çalışma biçimi MDN’de açıklanır. Ancak satıcıların ana review widget’larında Shadow DOM kullanıp kullanmadığı her zaman açık değildir; ayrıca SEO/structured data ihtiyaçları Shadow DOM kullanımını pratikte sınırlayabilir (bu nokta satıcıya göre değişir ve çoğunlukla “özel iç karar”dır).
3. **iframe ile izolasyon:** iframe, en güçlü izolasyonu sağlar; fakat erişilebilirlik, responsive yerleşim, iletişim (postMessage), SEO/structured data ve yükleme maliyeti açısından trade‑off’ları vardır. Bu rapor, satıcıların hangi widget’ta iframe kullandığını “resmi kaynak yoksa” varsaymaz.

### **Dinamik DOM’larda stabil kalma: MutationObserver, event delegation, lazy loading**

- **MutationObserver** DOM değişimlerini izlemek için tasarlanmıştır (eski Mutation Events’in yerine). Tema section’larının yeniden render olduğu (özellikle Shopify tema editörü, filtreleme, quick‑view) durumlarda “placeholder kayboldu → tekrar ekle” veya “placeholder eklendi → init” akışı için kullanılır.
- **Event delegation** (tek bir üst kapsayıcıya dinleyici bağlayıp alt eleman tıklamalarını `event.target` ile çözme) sık DOM değişen widget’larda dinleyici kopmalarını azaltır.
- **IntersectionObserver** ile **lazy loading**, reviews widget’ı sayfanın altındaysa ilk yükte ağır JS/HTML maliyetini düşürür; API, viewport kesişimini asenkron izlemeyi sağlar.
- Script yüklemede `async`/`defer` seçimi kritik olabilir. `defer`, DOM parse bittikten sonra fakat `DOMContentLoaded` tetiklenmeden önce çalışır; `async` ise indirir inmez çalışabilir ve sıra garantisi vermez.

### **Yerelleştirme ve erişilebilirlik**

- **Yerelleştirme (i18n/l10n):** Yotpo loader script’inin `languageCode` parametresiyle tema dilini aktarabilmesi, vendor widget’larının locale‑aware çalışması için resmi bir örnektir. Dil etiketleri tarafında web standardı BCP 47 / RFC 5646’dır.
- **Erişilebilirlik (a11y):** WCAG 2.x yönergeleri web erişilebilirliği için temel standardı oluşturur. İnteraktif widget’lar (ör. “Write a review” modal’ı) için WAI‑ARIA Authoring Practices modal dialog paterni; odak yönetimi, tab sırası ve dışarı kaçışı engelleme gibi kuralları tanımlar. Basit buton semantiğinde bile `role="button"` ve erişilebilir isim (`aria-label`) gibi ayrıntılar kullanıcı deneyimini belirler. Loox’un erişilebilirlik beyanı, WCAG 2.1’e atıf yapar (site seviyesinde).

## **Satıcı Analizi: Judge.me, Yotpo ve Loox**

Aşağıdaki satıcı analizleri, mümkün olduğunca **resmi dokümantasyon** ve birincil kaynaklara dayanır; satıcıların yayınlamadığı iç mimari detaylar “belirsiz/kapalı” olarak işaretlenir.

### **Judge.me**

**Resmi entegrasyon yöntemleri (Shopify):**

- **OS 2.0 / theme editor:** Widget’ları Shopify theme editor üzerinden app block ile ekleme yaklaşımı önerilir; “Liquid code ile kurulum advanced users only” şeklinde uyarı yapar.
- **Vintage themes:** Vintage tema tespitini (`index.liquid` vs `index.json`) ve bu temalarda hangi widget’ların desteklendiğini listeler; ayrıca “Judge.me app embed” etkinleştirme adımı içerir.
- **Platform‑independent:** Shopify dışı HTML sayfalarda kullanılabilecek placeholder örneklerini yayımlar (`jdgm-widget ... data-id=...`).

**API/SDK/snippet ve yükleme desenleri:**

- Judge.me API erişimi için `shop_domain` ve `api_token` (public/private ayrımı) dokümante edilir; public token’ın widget API’ye uygun olduğunu açıkça söyler.
- Entegrasyonlar için iki “display” modeli sunar: **Cache Server (Awesome plan, dakikalar içinde güncellenir, tek istekte çoklu widget)** ve **Widget API via cdn.judge.me (Free plan, ~20 dakikaya kadar güncelleme gecikmesi)**.
- Webhook doğrulaması için özel bir rehber yayımlar (imza doğrulama detayları bu rapor kapsamına “resmi dokümanla sınırlı” şekilde dahil edilmiştir).

**Moderasyon/spam/doğrulama:**

- Otomatik yayınlama ve rating kriteriyle yayınlama, “pending/spam” akışları resmi makalelerde anlatılır.
- “Verified” etiketinin otomatik uygulandığını ve manuel işaretleme yapılmadığını söyler; ayrıca “verified status” sınıflandırmasına dair açıklama yayımlar.
- Profanity filter yaklaşımını blog içeriğinde ayrıca detaylandırır (bu, “blacklisted words + custom words” desenini doğrular).

**Bilinen pitfall’lar ve tema uyumluluğu sorunları (resmi kaynaklardan):**

- Collection sayfasında otomatik “Install” butonu görünmüyorsa nedeni “tema yapısının otomatik yerleştirme için tanınmaması” olabilir; manuel Liquid snippet önerir.
- Tema kendi yıldızlarını gösteriyorsa Judge.me yıldızlarıyla **duplikasyon** oluşabilir; tema yıldızlarının devre dışı bırakılması gerektiğini belirtir.

## **Uygulama Reçetesi: Sağlam Enjeksiyon Kodları, SSR, Test ve Debug**

Bu bölümde amaç “hangi satıcı olursa olsun” tema bağımsız stabiliteyi artıracak pratik bir entegrasyon iskeleti sunmaktır. Kod örnekleri **vanilla JS** ve “çoklu tema” gerçeklerini (tekrar render, dinamik DOM, script duplikasyonu, performans) dikkate alır.

### **Sağlam widget enjeksiyonu için vanilla JS iskeleti**

Aşağıdaki iskelet; (1) script’i tek sefer yükler, (2) placeholder’ı güvenli şekilde yerleştirir, (3) dinamik DOM değişimlerinde tekrar dener, (4) görünür olunca lazy load eder. (Vendor‑spesifik `init` çağrıları ayrıca gösterilmiştir.)

```jsx
jsKopyala
/**
 * Vendor-agnostic widget injection scaffold.
 * - Loads external script once (dedup)
 * - Inserts placeholder near best anchor (multi-selector fallback)
 * - Re-inits on DOM mutations (throttled)
 * - Lazy-load via IntersectionObserver
 *
 * NOTE: Keep secrets server-side. Do NOT embed private tokens in browser JS.
 * Judge.me explicitly separates Public vs Private API Tokens. (Use private only server-side.)
 */
(function () {
  // ---------- Utilities ----------
  function loadScriptOnce(src, { id, attrs } = {}) {
    return new Promise((resolve, reject) => {
      // 1) Already loaded?
      const existing = id ? document.getElementById(id) : document.querySelector(`script[src="${src}"]`);
      if (existing) return resolve(existing);

      // 2) Create
      const s = document.createElement("script");
      if (id) s.id = id;
      s.src = src;
      s.async = true; // Typically preferred for third-party widgets (see vendor docs)
      if (attrs) Object.entries(attrs).forEach(([k, v]) => s.setAttribute(k, v));

      s.onload = () => resolve(s);
      s.onerror = () => reject(new Error(`Failed to load script: ${src}`));
      document.head.appendChild(s);
    });
  }

  function findAnchor(selectors) {
    for (const sel of selectors) {
      const el = document.querySelector(sel);
      if (el) return el;
    }
    return null;
  }

  function throttle(fn, waitMs) {
    let t = 0, timer = null;
    return function () {
      const now = Date.now();
      if (now - t >= waitMs) {
        t = now;
        fn();
      } else if (!timer) {
        timer = setTimeout(() => {
          timer = null;
          t = Date.now();
          fn();
        }, waitMs - (now - t));
      }
    };
  }

  // ---------- Config (example) ----------
  const config = {
    // Candidate anchors vary across themes.
    anchors: [
      ".product__title",
      "h1.product-title",
      "[data-product-title]",
      ".product-form",
      "main",
      "#MainContent",
      "body"
    ],
    // Placeholder container id to dedup
    placeholderId: "review-widget-slot",
  };

  function ensurePlaceholderMounted() {
    if (document.getElementById(config.placeholderId)) return true;

    const anchor = findAnchor(config.anchors);
    if (!anchor) return false;

    const slot = document.createElement("div");
    slot.id = config.placeholderId;
    slot.dataset.widget = "reviews";
    slot.style.minHeight = "24px"; // reduce CLS (layout shift) risk

    // Insert after anchor when possible; fallback append.
    if (anchor.parentNode) {
      anchor.parentNode.insertBefore(slot, anchor.nextSibling);
    } else {
      document.body.appendChild(slot);
    }
    return true;
  }

  // ---------- Lazy init ----------
  function initWhenVisible(initFn) {
    const slot = document.getElementById(config.placeholderId);
    if (!slot) return;

    if (!("IntersectionObserver" in window)) {
      // Fallback: init immediately
      initFn();
      return;
    }

    const io = new IntersectionObserver((entries) => {
      for (const e of entries) {
        if (e.isIntersecting) {
          io.disconnect();
          initFn();
          break;
        }
      }
    }, { root: null, threshold: 0.1 });

    io.observe(slot);
  }

  // ---------- Vendor-specific init examples ----------
  async function initYotpoExample({ appKey, instanceId, product }) {
    // 1) Ensure placeholder exists
    if (!ensurePlaceholderMounted()) return;

    // 2) Insert Yotpo widget instance placeholder per official pattern
    const slot = document.getElementById(config.placeholderId);
    slot.innerHTML = ""; // clear
    const div = document.createElement("div");
    div.className = "yotpo-widget-instance";
    div.setAttribute("data-yotpo-instance-id", instanceId);
    div.setAttribute("data-yotpo-product-id", String(product.id));
    div.setAttribute("data-yotpo-name", product.title);
    div.setAttribute("data-yotpo-url", product.url);
    div.setAttribute("data-yotpo-image-url", product.imageUrl || "");
    div.setAttribute("data-yotpo-description", product.description || "");
    slot.appendChild(div);

    // 3) Load script and init
    await loadScriptOnce(`https://cdn-widgetsrepository.yotpo.com/v1/loader/${appKey}`, {
      id: "yotpo-loader",
    });

    // SPA/dynamic DOM: official guidance says call initWidgets when new elements are added.
    if (window.yotpoWidgetsContainer && typeof window.yotpoWidgetsContainer.initWidgets === "function") {
      window.yotpoWidgetsContainer.initWidgets();
    }
  }

  async function initLooxExternalDomainExample({ shopMyshopifyDomain, productId }) {
    if (!ensurePlaceholderMounted()) return;
    const slot = document.getElementById(config.placeholderId);
    slot.innerHTML = `<div id="looxReviews" data-product-id="${String(productId)}"></div>`;

    await loadScriptOnce(`//loox.io/widget/loox.js?shop=${encodeURIComponent(shopMyshopifyDomain)}`, {
      id: "loox-loader",
    });
    // Loox loader typically scans known ids/classes; explicit init API is not officially required in the cited doc.
  }

  // ---------- Bootstrapping & rehydration ----------
  const recheck = throttle(() => {
    // Ensure placeholder remains (themes can rerender sections)
    const mounted = ensurePlaceholderMounted();
    if (!mounted) return;
    // You can optionally re-init vendor here if vendor requires it after DOM changes (e.g., SPA).
  }, 500);

  // DOM ready-ish
  ensurePlaceholderMounted();

  // Re-mount on DOM changes
  if ("MutationObserver" in window) {
    const mo = new MutationObserver(recheck);
    mo.observe(document.documentElement, { childList: true, subtree: true });
  }

  // Example usage:
  // initWhenVisible(() => initYotpoExample({ appKey: "...", instanceId: "...", product: {...} }));
  // initWhenVisible(() => initLooxExternalDomainExample({ shopMyshopifyDomain: "store.myshopify.com", productId: 123 }));
})();
```

Bu iskelette kullanılan tarayıcı API’ları için standard referanslar: MutationObserver (DOM değişim izleme) ve IntersectionObserver (lazy init) MDN’de tanımlıdır; script yükleme davranışında `async/defer` semantiği yine MDN’de anlatılır.

### **SSR (Server‑Side Rendering) ve headless senaryoları**

Headless storefront’larda iki temel yol vardır:

**Yol 1 — Vendor widget’ı client‑side çalıştırmak:**

En hızlı kurulumdur; ancak bundle yükü, CLS riskleri ve “SPA re-init” gibi konulara dikkat gerektirir. Yotpo, SPA senaryosunda açıkça `initWidgets()` ister; bu, route değişimlerinde entegrasyon kodu yazmanız gerektiğini gösterir.

**Yol 2 — SSR’da review özetini “server’dan çekip” render etmek (hydrate opsiyonel):**

Özellikle PDP üst kısmındaki yıldız özeti gibi küçük bileşenlerde performans avantajı sağlar. Yotpo, headless entegrasyon rehberinde “bottomline” endpoint’iyle yıldız özetini API üzerinden çekmeyi önerir.  Judge.me’de benzer şekilde storefront içeriği için cache server/widget API ayrımı bulunur; ayrıca public/private token ayrımı “server‑side’da private token” ilkesini destekler.

SSR için pratik öneriler:

- Bir “Reviews Summary” endpoint’i oluşturup (Edge/Node/Serverless), vendor API/CDN’den aldığınız sonucu **cache** edin (örn. 30–300 sn TTL + stale‑while‑revalidate).
- Private token gerektiren çağrılar **asla browser’dan yapılmamalıdır** (Judge.me private token uyarısı).
- Structured data/SEO gerekiyorsa vendor’un sağladığı structured data yöntemlerini ayrıca kontrol edin (bu rapor, vendor‑özel JSON‑LD detaylarını resmi kaynakta açıkça verilmedikçe varsaymaz).

### **Tema‑çeşitliliğinde test ve debug stratejileri**

Tema farklılıkları nedeniyle “repro” yakalamak için sistematik bir test matrisi gerekir:

1. **Yerleşim testleri:** PDP, collection grid, home featured products, quick‑view modal, search results, cart drawer. Judge.me, collection sayfasında otomatik yerleştirmenin tema yapısı nedeniyle başarısız olabileceğini ve manuel kod gerektiğini doğrudan söyler; bu tip sayfalar özellikle test edilmelidir.
2. **Tema değişimi regresyonu:** Loox ve Judge.me, tema değişince widget’ların yeniden kurulması gerektiğini vurgular; “tema upgrade” senaryosunu CI/regresyon listesine ekleyin.
3. **Duplikasyon ve çakışma:** Judge.me, tema yıldızlarıyla kendi yıldızlarının duplikasyon oluşturabileceğini anlatır; aynı anda birden fazla reviews app kalıntısı kalıp kalmadığını da kontrol edin.
4. **Network/Performance:** Üçüncü taraf script’ler render’ı geciktirebilir; `async/defer` semantiğini doğru uygulayın.
5. **SPA/dinamik DOM:** Yotpo gibi vendor’lar re-init ihtiyacını resmi olarak belirtir; route değişimlerinde “widget placeholder yeniden eklendi mi?” ve `initWidgets()` çağrısı doğru yerde mi kontrol edin.
6. **Gizlilik ve güvenlik:** DPA/sub‑processor ve veri silme akışlarını “data subject request” senaryolarıyla test edin. Loox DPA, silme talebi ve ihlal bildirimi gibi süreçleri sözleşmesel olarak tanımlar; Yotpo ve Judge.me de benzer dokümantasyon yayımlar.

Bu yöntem, gerçek vendor script’lerine bağlı olmadan “insertion etkisini” görselleştirir ve tema CSS çakışmalarını hızlıca teşhis etmeye yardımcı olur.

## **En İyi Uygulamalar Kontrol Listesi ve Karar Kriterleri**

Aşağıdaki kontrol listesi, “arbitrary theme” gerçekliğiyle uyumlu, satıcıdan bağımsız mühendislik pratiklerini özetler:

| **Kontrol** | **Neden** | **Pratik ölçüt** |
| --- | --- | --- |
| App block/app embed’i tercih et | DOM selector kırılganlığını azaltır; Shopify resmi olarak bu modeli önerir | OS 2.0 temalarda widget app block ile taşınabiliyor mu? |
| Script’i tekil yükle (dedup) | Duplikasyon performans ve UI bug üretir | `id` ile script singleton, birden fazla tema include’u engelle |
| Lazy load (IntersectionObserver) | PDP altındaki ağır widget’ı LCP/TTI’a daha az zarar verir | IO API ile görünür olunca init |
| Dinamik DOM’da re-init | Tema/SPA re-render’larında widget kaybolabilir | Yotpo SPA için `initWidgets()` resmi gereksinim |
| CLS azalt | Reviews widget geç render olunca layout kayar | Placeholder’a min-height, skeleton |
| CSS scope/namespace | Tema CSS’i widget’ı bozabilir | Prefiksli class, sınırlı override; Shadow DOM seçeneklerini değerlendirin |
| i18n standardı | Çok dilli mağazalarda dil uyumu gerekir | BCP 47 / RFC 5646 tag’leri ve vendor language parametreleri |
| a11y semantiği | Widget’lar sık modallar/etkileşim içerir | WAI‑ARIA modal pattern + erişilebilir isimler |
| Secret’ları server-side tut | Browser’da private token sızıntısı kritik risk | Judge.me public/private token ayrımı |
| GDPR/DPA/sub‑processor görünürlüğü | Hukuki ve güvenlik denetimleri için temel | DPA + sub‑processor listesi var mı? |
| Tema değişimi runbook’u | Tema upgrade’leri widget’ı düşürebilir | Loox/Judge.me tema değişimi sonrası re-install notları |

Karar kriteri olarak, “sadece güzel widget” yerine şu teknik soruların yanıtını aramak genellikle daha iyi sonuç verir:

- Headless/harici domain desteğine ihtiyacım var mı? Loox bunu allow‑list + snippet ile resmi olarak destekler; Yotpo headless için API‑based rehber sunar.
- Moderasyon/spam kalitesi ve doğrulama politikası güven veriyor mu? Judge.me ve Loox bu konuda resmi politika/metin yayımlar; Yotpo Shopify listelemesinde sentiment/profanity check sunar.
- Performans güncelleme gecikmesi önemli mi? Judge.me “Cache Server vs Widget API” güncelleme süresi farkını açıkça yazar.
- Sözleşmesel gizlilik (DPA), alt‑işleyen listesi, silme/ihlal bildirim süreçleri net mi? Loox DPA, Yotpo DPA ve Judge.me GDPR/sub‑processor dokümanları bu açıdan incelenebilir.
